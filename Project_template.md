# Project Template

## Задание 1. Исследование моделей и инфраструктуры

### 1) Сравнение LLM: локальные Hugging Face vs облачные DeepSeek/OpenAI/YandexGPT

| Критерий | Локальные Hugging Face (например, Llama/Qwen/Mistral) | DeepSeek API | OpenAI API | YandexGPT API |
|---|---|---|---|---|
| Качество ответов | Сильно зависит от выбранной модели и дообучения; для корпоративных FAQ обычно хорошее, но ниже топовых облачных моделей без тюнинга | Высокое качество в задачах общего назначения и кода, достаточное для RAG FAQ | Стабильно высокое качество и хороший follow-up в сложных вопросах | Хорошее качество на русском, удобно для русскоязычных сценариев |
| Скорость | Зависит от GPU/квантизации; на CPU может быть медленно | Высокая, зависит от API-лимитов и сети | Высокая, масштабируется провайдером | Высокая, зависит от тарифа и нагрузки |
| Стоимость владения | Нет платы за токены, но есть CAPEX/OPEX на сервер, DevOps и поддержку | OPEX за токены, часто выгодно для MVP | OPEX за токены, минимальный вход по инфраструктуре | OPEX за токены, минимальный вход по инфраструктуре |
| Развёртывание | Сложнее: инференс-сервер, мониторинг, обновления модели | Простое: API-ключ + SDK | Простое: API-ключ + SDK | Простое: API-ключ + SDK |
| Конфиденциальность | Максимальный контроль данных (on-prem/VPC) | Данные уходят внешнему провайдеру (нужна политика безопасности) | Данные уходят внешнему провайдеру (нужна политика безопасности) | Данные уходят внешнему провайдеру (нужна политика безопасности) |

Вывод по LLM:
- Если приоритет: минимальные риски утечки и контроль данных, то лучше локальная/приватная LLM.
- Если приоритет: быстрое внедрение и качество «из коробки», то облачная модель выигрывает по time-to-market.

### 2) Сравнение эмбеддингов: локальные Sentence-Transformers vs OpenAI Embeddings

| Критерий | Sentence-Transformers (локально) | OpenAI Embeddings (облако) |
|---|---|---|
| Скорость индексации | Высокая на GPU, приемлемая на CPU для средних объёмов | Высокая, но зависит от API-лимитов и сети |
| Качество поиска | Хорошее на доменных текстах при правильном выборе модели | Стабильно высокое мультиязычное качество |
| Стоимость | Нет платы за токены, но есть стоимость железа/поддержки | Плата за объём токенов при каждой индексации/переиндексации |
| Управляемость | Полный контроль, можно запускать офлайн | Очень просто в интеграции, но внешняя зависимость |

Вывод по эмбеддингам:
- Для данной задачи с постоянным ростом базы (≈400 страниц/мес) локальные эмбеддинги выгоднее в долгую.
- `all-MiniLM-L6-v2` подходит как быстрый и экономичный старт (384 dim, низкая латентность).

### 3) Сравнение векторных БД: ChromaDB vs FAISS

| Критерий | ChromaDB | FAISS |
|---|---|---|
| Скорость индексации/поиска | Хорошая, но есть накладные расходы БД-слоя | Очень высокая, особенно для in-memory и ANN-сценариев |
| Сложность внедрения | Удобная developer experience: коллекции, метаданные, persistence | Минималистично и быстро, но больше ручной логики вокруг хранения/метаданных |
| Поддержка | Проще стартовать и развивать функциональность | Требует аккуратной обвязки (сохранение индекса, метаданные, миграции) |
| Стоимость инфраструктуры | Низкая, но чуть тяжелее стек | Минимальная для пилота/PoC |

Вывод по векторной БД:
- Для пилотного RAG и максимальной скорости разработки достаточно FAISS.
- Для продуктовой БД с богатой работой с коллекциями и фильтрами Chroma удобнее, но не обязательно на старте.

### 4) Варианты целевой архитектуры (3-4 варианта)

#### Вариант A (облачная LLM + локальные эмбеддинги + FAISS)
- LLM: DeepSeek API
- Эмбеддинги: `all-MiniLM-L6-v2` (локально)
- Векторная БД: FAISS
- Плюсы: быстрый запуск, низкая стоимость индексации, хорошая скорость, стек простой для MVP.
- Минусы: зависимость LLM-части от внешнего API.

#### Вариант B (максимальная конфиденциальность)
- LLM: локальная HF-модель (например, Qwen/Llama Instruct 7B-14B)
- Эмбеддинги: `bge-small`/`all-MiniLM-L6-v2` локально
- Векторная БД: FAISS
- Плюсы: полный контроль данных, офлайн-режим.
- Минусы: выше требования к GPU и DevOps.

#### Вариант C (максимально простой enterprise API-старт)
- LLM: OpenAI или YandexGPT
- Эмбеддинги: OpenAI Embeddings
- Векторная БД: ChromaDB
- Плюсы: минимум инфраструктуры, быстрое MVP.
- Минусы: регулярные API-расходы, риск vendor lock-in, вопросы комплаенса.

#### Вариант D (гибрид для роста)
- LLM: облачная (DeepSeek/OpenAI/YandexGPT)
- Эмбеддинги: локальные (`all-MiniLM-L6-v2`)
- Векторная БД: ChromaDB (на старте) с возможностью миграции на FAISS/Qdrant
- Плюсы: баланс удобства и стоимости, проще масштабировать функции фильтрации.
- Минусы: архитектура чуть сложнее, чем A.

### 5) Рекомендованная конфигурация сервера

#### Для Варианта A (DeepSeek + MiniLM + FAISS)
- CPU: 8 vCPU
- RAM: 32 GB
- GPU: не обязателен (достаточно CPU для `all-MiniLM-L6-v2` на объёме задачи)
- Disk: SSD 200+ GB

Почему так:
- Индексация 20k+ документов на MiniLM выполнима на CPU, хотя медленнее, чем на GPU.
- 32 GB RAM достаточно для индекса + приложения + служебных процессов при пилотной нагрузке.

#### Если планируется локальная LLM (Вариант B)
- CPU: 16 vCPU
- RAM: 64 GB
- GPU: от 24 GB VRAM (например, 1x L4/RTX 4090 class)
- Disk: SSD 500+ GB

### 6) Итоговый выбор для кейса QuantumForge

С учетом требований кейса (быстрый запуск, рост базы знаний, контроль затрат, приемлемый уровень конфиденциальности) оптимальным является:
- LLM: **DeepSeek API**
- Embeddings: **`sentence-transformers/all-MiniLM-L6-v2`**
- Vector DB: **FAISS**

Почему этот вариант лучше остальных:
- По сравнению с полностью облачным стеком (вариант C) ниже регулярные расходы за счет локальной генерации эмбеддингов и дешевле переиндексация при росте контента.
- По сравнению с полностью локальным стеком (вариант B) существенно проще внедрение и ниже требования к инфраструктуре на старте.
- По сравнению с гибридом на Chroma (вариант D) проще эксплуатация в MVP-контуре при сопоставимом качестве retrieval.
- Сохраняет практичный путь масштабирования: при ужесточении требований безопасности можно заменить только LLM-слой на локальный без полной перестройки пайплайна.

### 7) Выбор векторной БД

Для создания бота планируется использовать **FAISS**, потому что:
- высокая скорость поиска и индексации;
- минимальные инфраструктурные затраты;
- простая интеграция с LangChain;
- достаточно функциональности для MVP.
